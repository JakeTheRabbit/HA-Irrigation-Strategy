# Operator dashboard UI implementation

Date: 2026-09-07

## Delivered

The primary operator UI is a React application using checked-in shadcn/Radix controls, Lucide icons and Recharts. Source is divided between `frontend/src/App.tsx`, `frontend/src/components/dashboard.tsx`, seven modules in `frontend/src/pages/`, and `frontend/src/styles.css`.

- Overview: explicit connection/demo state, controller scheduling state, actionable room notices, controller-derived summary metrics, recorded moisture history, zone table, latest events and direct workflow navigation.
- Zones: search, table/card views and accessible detail Sheet; controller-derived readings, sensor entities and reviewed scheduling switch changes.
- Irrigation strategy: existing number settings grouped by controller phase and selected zone, available steering-mode choices, local drafts, bounds/step/options validation, before/after review, verified apply and retained failed drafts. Poll updates never replace drafts. Controller changes that occur while drafting are called out for number fields.
- Activity: event/zone/search filters and export of exactly the filtered records as CSV. Time-only records retain their reported time and explicitly show that no date was recorded.
- Sensors: search, availability filters, reported readings, entity names and timestamps; reporting is distinguished from calibration/freshness verification.
- Settings: connection form, session token handling delegated to the adapter, room scheduling review and persisted light/dark appearance.
- Help: plain-language phase and metric glossary, documented safety semantics and existing specialist screens.

The desktop sidebar collapses into an accessible Sheet on mobile. Distinct form IDs avoid duplicate labels. Pages support hash navigation and browser back/forward. Dirty navigation and room changes require explicit discard. Browser refresh/tab close warns while drafts exist. Specialist URLs use actual classic view IDs, preserve room/demo context and legacy specialist query views redirect to the corresponding classic screen.

## Safety and state behavior

UI writes use entity IDs received through the Controller interface; no entity IDs are constructed. Only existing number settings, supported steering-mode choices, and room/zone configuration switches can be reviewed. Direct pump, valve or manual-shot buttons are absent. Scheduling pause is explicitly described as potentially affecting future cycles without interrupting an active shot.

Live failures are never converted into demo data. Unavailable readings remain unavailable, historical load/empty/error states have explanations, offline state labels retained values as last received, and all live writes are disabled while offline/connecting. VWC references use phase-specific metric labels, avoiding presentation of an overnight emergency floor as a daytime target.

## Practical limits

Event history is restricted to controller-exposed records. Time-only log entries have no inferred date. Settings are shown only when discovered, and classic specialist controls retain their existing behavior and scope. Strategy drafts are intentionally tab-local and are not persisted across browser reload.
