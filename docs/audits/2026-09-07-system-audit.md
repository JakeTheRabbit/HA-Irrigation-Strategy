## Bounded controller fixes completed locally

- **Timing:** the shot deadline now uses `time.monotonic()`, starts before the valve-open request, and includes HA read latency. Each read is limited to the smaller of two seconds or remaining time. Volume estimates include elapsed time and conservatively include the valve-close acknowledgement delay; request overruns are no longer hidden by a 100% clamp. Socket scheduling and physical device response can still exceed software request timeouts, so this is not a guaranteed physical shutdown deadline or flow-meter measurement.
- **Blind budgets:** a fallback or copied shot is blocked when that blind zone has reached its own daily cap. A healthy sibling's measured emergency does not give the blind row an emergency exemption. The pure engine's existing live-probe emergency exceptions remain unchanged. The existing budget semantics are preserved: a shot can start below the daily cap and cross it; this change prevents further blind shots once at/over the cap.
- **Hardware holds:** any failed/unknown normal close, or unconfirmed close during error cleanup, latches a hardware fault. The fault blocks the room and other rooms sharing its recorded hardware. It is atomically persisted as optional `_hardware_fault` metadata within the room's existing state block; old flat/nested state files and existing counters still load. Malformed fault metadata is held safely instead of silently clearing it. Restart/rebuild does not clear a saved fault.
- **Discovery-independent durability (independent-review correction):** saved room blocks are retained separately from discovered `Room` objects. Temporarily absent descriptors cannot drop fault metadata, zone counters, or unknown room metadata during a save. An absent owner's recorded hardware continues to block matching active rooms; unrelated hardware remains usable. An orphan fault with unusable hardware identifiers holds conservatively until discovery returns. Orphaned holds cannot auto-clear: the owner must be rediscovered and pass the existing disarm/readback recovery checks. The regression covers restart with an absent named room, an intervening save, retained unrelated room data, restored owner counters/metadata, and eventual verified recovery.
- **Recovery policy:** the fault owner AND every currently configured engine sharing its recorded hardware must read **OFF**, and every recorded/current affected hardware entity must read exactly **OFF**. Unknown/unavailable is insufficient. Only then is the hold durably cleared, while all affected engines remain disarmed; subsequent operation requires explicit rearming. If clearing cannot be saved, the in-memory hold remains. A failure to persist the initial fault emits a critical warning that restart protection is unavailable until storage is repaired.
- **GUI telemetry:** `sensor.crop_steering_<prefix>ai_heartbeat.attributes.hardware_fault` now contains the hold reason or null, including holds from a room sharing hardware. `app_status` reports `error` while held even when no shot is due. Engine OFF and manual override ON remain the only in-flight interruption controls; zone/system/auto OFF retain their previous meaning of preventing subsequent shots. Manual-event and room-recipe findings remain unresolved in backend services and should not be offered as verified controls by the replacement UI.

Before the final discovery-retention correction, **88 integration tests passed** in the concurrently updated checkout and **46 pure-engine tests passed**. ## Baseline high-impact findings (before fixes)

1. **P1 — Network latency extends irrigation beyond its configured duration.** `addons/f2_control/f2_control/controller.py:969-978` performs two synchronous HA reads per two-second slice, then increments `elapsed` only by the sleep. Both requests run while the valve is open. With one second per read, an offline clock simulation requested 6 seconds, returned 6 seconds delivered, but consumed 12 seconds of wall time. HA requests can each wait eight seconds (`:59`), so the claimed hard duration cap and volume accounting are not wall-clock bounds. Use a monotonic deadline, bounded remaining-time requests, and actual measured valve-open duration for accounting. Existing interruption tests mock reads as instantaneous and miss this failure.

2. **P1 — Blind irrigation bypasses the daily water cap.** `controller.py:1323-1347` creates fallback/copy decisions without calling `decide()`, where the budget check resides (`crop-steering-engine/src/crop_steering_engine/core.py:236-237`). Neither `_blocked` nor `_act_zone` imposes a budget. An offline `_loop_room` simulation with a dead probe, 1,000 L already delivered, a 10 L cap, and the fallback interval elapsed produced `fire=True`, `block=None`. This is ordinary blind fallback, not a measured emergency. Apply common budget and interval checks to every actuation path, allowing exemptions only for an explicit validated emergency. Existing blind tests cover sensor-name compatibility and time-based phases, not fallback budgets.

3. **P1 — A failed valve close does not inhibit the next shot.** `controller.py:1030-1053` alerts about unknown/stuck closure, then counts the shot; `:1065-1066` clears busy and the outer loop can proceed to another zone. Opening the shared pump/mainline for that subsequent shot can also feed the first, still-open row. Add a room/shared-hardware fault latch, require explicit OFF readback for relevant hardware, and block subsequent pumping until safely cleared. Existing controller tests confirm normal closure and kill interruption, not a stuck valve followed by another zone's demand. This finding is based on control flow; no hardware failure was induced.

4. **P1 — Manual actions report success without any consumer in this controller.** `www/f2.html:2671-2673` posts `crop_steering_manual_irrigation`; `:6498` reports “shot fired” after the event POST succeeds. `custom_components/crop_steering/services.py:218-240` emits `crop_steering_irrigation_shot`; custom shots, phase changes, override timeout events and trigger buttons similarly publish events. The shipped controller only polls REST (`controller.py:1653-1668`) and has no event subscription. It also does not read the integration irrigation-phase select or documented phase-control helper. In this checkout the actions do not implement their promised controller result. An external legacy listener could still act on the event, so it is unsafe to assume either a no-op or current safety gates in production. Keep unsupported actions unavailable in the replacement UI until a room-scoped, validated, acknowledged controller command path exists. Service tests prove events/entities changed, not controller execution. The override switch itself does work, but its advertised timeout does not.

5. **P1 — Recipe services cross room boundaries.** `custom_components/crop_steering/services.py:419-420` applies a stage to every loaded manager; `:450-451` overwrites every room recipe. The schemas (`:141-150`) accept no room. A room-focused editor using those services would change unrelated rooms. Use the per-room `select.recipe_stage` entity for room-local stage application. Saving requires a backwards-compatible room-aware service before it can be safely offered as a room-local operation. Existing recipe tests cover pure target prefixes and service tests cover absent stores, not a two-room save/apply isolation contract.

6. **P2 — Disable controls have different in-flight semantics.** `_blocked` checks engine, system, auto, zone and manual override (`controller.py:867-880`), but `_wait_shot` only checks engine kill and manual override (`:969-975`). Turning off zone/system/auto during a running shot does not stop that shot. A replacement UI must distinguish “pause future shots” from the room engine stop and must not promise a two-second stop, because synchronous network requests extend it. If the intended behaviour is immediate disable for all controls, centralize and test the in-flight gate. Existing tests cover only engine kill and override.

## Safe frontend contract for this checkout

- **Transport/auth:** add-on nginx is a static server at ingress port 8420, with no LAN port publication in `addons/f2_control/config.yaml`. It has no API proxy or frontend credential endpoint. Use the authenticated HA frontend's state/service connection when embedded, or an explicit HA-origin authenticated client. Do not bake tokens into assets or put bearer credentials in query strings. A successful HA service/event response is acknowledgement of that HA request, not proof of physical delivery.
- **Discovery:** enumerate HA states and find `sensor.crop_steering_*engine_config` with attributes `slug`, `prefix`, `num_zones`, `pump`, `mainline`, `valves`, `enable_flag`, `feed_ec_sensor`, `feed_ph_sensor`. Read the explicit prefix; default is empty, named rooms are e.g. `veg_`. Zone numbers run from 1 through `num_zones`; descriptor valve keys can be JSON strings. Friendly names and `f1`/`f2` are not routing contracts. Do not invent a default room when discovery is absent.
- **Engine stop/enable:** `sensor.crop_steering_<prefix>ai_heartbeat.attributes.enable_flag` identifies the flag the engine actually uses and takes precedence over the descriptor fallback. Default is usually `input_boolean.f2_control_enabled`; named rooms normally use `switch.crop_steering_<prefix>engine_enabled`. Dispatch `input_boolean.turn_on/turn_off` or `switch.turn_on/turn_off` according to the discovered entity domain. Do not invent a default-room engine switch. Require a current readable flag and room descriptor before enabling.
- **Other switches:** `switch.crop_steering_<prefix>system_enabled`, `auto_irrigation_enabled`, `zone_<n>_enabled`, `zone_<n>_manual_override`, `ec_stacking_enabled`. Manual override ON holds automatic irrigation; OFF resumes eligibility. Current controller does not enforce its timeout event.
- **Live setpoints:** `number.crop_steering_<prefix>zone_<n>_<param>`; controller falls back to `number.crop_steering_<prefix><param>` when per-zone values are missing/unavailable. Use `number.set_value` with the exact discovered entity ID and a finite numeric value. Honour each entity's `min`, `max`, `step`, and unit attributes, then read back. Updating a global number does not override an existing per-zone number. Surface whether a field is zone-specific or a global fallback.
- **Primary parameters actually read:** `p1_target_vwc`, `p2_vwc_threshold`, `p2_shot_size`, `p1_initial_shot_size`, `p1_shot_size_increment`, `p1_maximum_shots`, `p1_time_between_shots`, `vegetative_dryback_target`/`generative_dryback_target`, `p0_maximum_wait_time`, `ec_target_{veg|gen}_p0/p1/p2`, `p3_emergency_vwc_threshold`, `p3_emergency_shot_size`, `max_daily_volume`, `field_capacity`, `maximum_ec`, `watchdog_hours`. Sizing: `zone_<n>_substrate_volume` is L per plant, `zone_<n>_plant_count`, `zone_<n>_drippers_per_plant`, and room-global `dripper_flow_rate` is L/hour per dripper. Room-global `lights_on_hour`, `lights_off_hour`, `irrigation_ec_min/max`, `irrigation_ph_min/max`, `max_shot_duration` are read directly. Not every integration entity affects this engine.
- **Steering modes:** `select.crop_steering_<prefix>zone_<n>_steering_mode` and room `select.crop_steering_<prefix>steering_mode`; use discovered options, not a guessed label. The room-local recipe stage is `select.crop_steering_<prefix>recipe_stage`, options `Veg`, `Transition`, `Bulk`, `Ripen`, `Custom`. Its attributes include `params`, `stages`, `active_stage`; `select.select_option` applies only that room's manager. Current application can partially fail while still setting the active stage (`recipe.py:96-115`), so verify affected number values before claiming completion.
- **Telemetry:** fused VWC/EC uses current `sensor.crop_steering_<prefix>{vwc|ec}_zone_<n>` or legacy `sensor.crop_steering_<prefix>zone_<n>_{vwc|ec}`. Probe the current ID first, then legacy. Controller outputs include `zone_<n>_phase`, `zone_<n>_status`, `zone_<n>_safety_status`, `zone_<n>_daily_water_app` (L), `zone_<n>_irrigation_count_app`, `zone_<n>_last_irrigation_app`, `zone_<n>_vmax_detected`, `prediction_zone_<n>_next_irrigation_hours`, `app_status`, `ai_heartbeat`, `current_decision`, `activity_log`. Prefix all with `sensor.crop_steering_<prefix>`. Treat missing/unavailable/stale values as unknown, never zero or healthy. Activity/current decision are scheduling output, not confirmed physical shot completion; `_busy` has already cleared before status publication. Use actual mapped hardware states for a live-running indicator, with unavailable clearly shown.
- **Existing services/events:** `transition_phase` accepts target P0–P3, optional room/reason/forced; `execute_irrigation_shot` accepts zone, duration_seconds 1–3600, optional room and shot_type P1/P2/P3_emergency; `custom_shot` accepts target_zone, volume_ml 10–10000, optional room/intent/target_runoff_pct/tag; `set_manual_override` accepts zone, optional room/enable/timeout_minutes 1–1440. These schemas describe event routing and entity writes only, not a verified actuation interface. No manual-shot event should be sent by the replacement UI merely because the service is present.
