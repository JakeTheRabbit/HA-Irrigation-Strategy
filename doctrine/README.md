# Crop-steering doctrine pack

The generic crop-steering knowledge the optional AI brain will get in its cached system prompt: what the engine
does (checked against the code on every build), what each of the brain's acting answers does, how to read the
symptoms, and the agronomy rules, each with an evidence class and its sources.

**The AI assistant reads this pack** (`brain_provider: claude_haiku`). Its prompt module
(`addons/f2_control/f2_control/jev/prompt.py`) reads a generated copy of `compiled/` placed beside the controller
code (the app's build context cannot reach the repository root), `addons/f2_control/f2_control/doctrine/`. The
pack is advice to the brain; the engine and the brain's guard decide what moves water, so a change here never
changes watering on its own.

## How it is built

`doctrine.rules.json` and `denylist.public.txt` are the hand-edited data; this README, `LICENSE` and the build
script are hand-written too. Everything else here is generated by `tools/build_doctrine.py` (Python standard
library only):

```
python doctrine/tools/build_doctrine.py --private-skip "local run"     # validate, regenerate, compile, lint, write
python doctrine/tools/build_doctrine.py --check --private-skip "..."   # fail if any generated file is stale
python doctrine/tools/build_doctrine.py --check --private-denylist FILE
```

The build reads the code of the repository it sits in: the engine's `core.py`, the one
`addons/*/*/controller.py`, the brain package beside it (`jev/doctrine.py`, `jev/envelope.py`, `jev/judges/*.py`,
`jev/triage.py`), `jev_bridge.py`, `auto_setpoints.py` and the integration's `number.py`. `--repo` points it at
another checkout, and each path has its own flag (`--core`, `--controller`, `--jev`, `--brain`, `--bridge`,
`--auto`, `--numbers`, `--controller-copy`).

The build fails when any of these checks fails:

1. **Rules valid.** Ids are unique, every rule carries one evidence class, every source id resolves, every
   decision names a rule, and every symptom lever tagged `ACTS` names a decision and an answer key that **acts**
   in it (`via`), taken from the decision catalogue. An answer that acts on nothing cannot be an `ACTS` lever.
2. **JEV audit.** Every one of the 123 rules in the brain package's `jev/doctrine.py` (99 owner-written plus 24
   from a vendor handbook) is either merged into a doctrine rule (`merged_from`) or listed under `dropped` with a
   reason.
3. **Statements come from the code.** 46 statements are checked:
   - 24 about `decide()`, each by **calling** the engine on constructed scenarios (constants, bounds and cap
     exemptions are read from the module). PH-8 to PH-10 pin down what `dryback_target` does and does not do;
     PH-11 reads the integration's default dryback targets and P0 wait from the engine's `defaults.py`; IR-2 shows that a
     maximum-EC block or hold stops every other shot on that tick.
   - 14 controller and integration facts (CT-1 to CT-14), checked against the source text of `controller.py`,
     `auto_setpoints.py` and `number.py`. CT-14 also calls `zone_safety_status()`. These are **text checks**:
     they prove the guarding lines are present, not the behaviour around them. CT-5's sibling copy and budget and
     CT-7's close-and-save, for example, rest on a constant and a signal handler being there.
   - 7 about the brain's guard and levers (BR-1 to BR-7): the build **calls the envelope's `admit()`** on
     constructed cases for every directive kind and reads the setpoint bands, the levers, the band centre, the
     grow-plan lock-out and the revert pause from the judges and `jev_bridge.py`. BR-7 checks that every answer
     key the catalogue names exists in the judges' questions.
   - The `ec_adjust` table, by calling the function.

   The six helper lines in the engine section (`cross_zone_outliers`, `detect_vmax`, `pick_sibling`,
   `zone_safety_status`, `validate_params`, and the status-tile words) are not checks: the tile words are read
   by calling `zone_status_label()`, the other five are written out and reviewed by hand.

   If the code changes so that a checked sentence is no longer true, the build fails until the sentence is
   reworded. The generated files hold what the pack states, never raw bytes or hashes of the code, so a comment
   or an unrelated edit in those files changes no output.
4. **Strip lint, two layers.** Every output, `doctrine.rules.json`, this README and the scripts in `tools/` are
   searched.
   - The **public** list, `denylist.public.txt`, ships with the pack and always runs, on fork pull requests too.
     It holds **patterns** (scope `all`): entity ids, IP addresses, messaging credentials, dated heartbeat logs,
     local absolute paths, email addresses, phone numbers in international form, titled person names, **room ids
     as whole tokens** (a capital letter followed by one or two digits; the phases `P0` to `P3` are exempt), and
     **URLs outside an allowlist** of the hosts the sources cite (a new source on another host adds its host in
     the same change). Because the room-id pattern matches any such token, plan ids of that shape are written out
     in words in every linted file. Its one set of words is the vendor and product names the sources actually
     cite (scope `cited`, OD-9): they may appear only in the `sources` object of `doctrine.rules.json` and in
     `09-sources.md`. Source ids are neutral (`VND-*`, `GL-*`, `OSS-CTRL`), so the names never reach a rule, an
     id, a default or a compiled prompt.
   - The **private** list holds every forbidden word and phrase: a site's own room, staff and company names, its
     numbers, and the third-party names and phrases this project never ships. It is read from a file
     (`--private-denylist FILE`, or the `DOCTRINE_PRIVATE_DENYLIST` environment variable); CI writes it from a
     secret. When it is missing or empty the build **fails** ("private denylist secret missing"). Only
     `--private-skip REASON` turns it off, for a run where no secret exists (a fork pull request, a contributor's
     machine); the skip is printed and written to the job summary. The public list itself is linted with the
     private one, so it cannot carry a word it exists to keep out.
   - A `vendor-snapshot/` folder inside the pack fails the build: audit inputs that hold site text never ship.
5. **Generated files current** (`--check`): every output matches, and no file is left in `compiled/` that the
   build no longer produces (a write run deletes such files). An output goes stale only when a value the pack
   prints changes: from `core.py` (constants, parameter bounds, cap exemptions, the `ec_adjust` table, the
   status-tile words, the assumed feed EC default) or from `defaults.py` (the default dryback targets and P0 wait
   that PH-11 quotes).
6. **Controller copy.** When the controller's copy of `compiled/` exists (`addons/<app>/<package>/doctrine/`),
   `--check` compares it byte for byte with `compiled/` (a one-byte edit, a missing file or an extra file fails)
   and a write run rewrites it. Until then the build prints "controller doctrine copy: none yet, skipped", so the
   CI step needs no change when the copy arrives. The stage arcs are the one arc source: the controller's
   `stage_rows()` reads the tables in its copy (`arcs/`), and the build also writes the same rows as data to the
   dashboard's `frontend/src/lib/generated/arcs.json` whenever the dashboard source exists, where `--check` fails
   on a one-byte difference too.

The hashes of the code files a run was checked against are printed in the log and the job summary
(`checked against: core ..., controller ...`), never written to a generated file.

### What a change to the code owes this pack

- A change to a value the pack prints (from `core.py`, or `defaults.py`'s default dryback targets and P0 wait)
  regenerates `02-engine-rules.md`, `engine-rules.generated.json` and `compiled/` in the same commit, and the
  controller's copy once it exists.
- A change that makes a checked sentence false in `core.py`, the controller, `jev_bridge.py`,
  `auto_setpoints.py`, the envelope, a judge or `number.py` rewords the rule in the same commit.
- Any other edit to those files needs nothing.
- Check 2 expects `jev/doctrine.py` with `RULES` and exactly one second `*_RULES` table, and audits by position
  (`jev:topic#i`). Rewording a rule there passes silently, and inserting or deleting one shifts the refs. The pull
  request that renames that table, edits its rules or retires the package rewrites check 2 and the `merged_from`
  refs in the same commit.

### Tests

`tests/test_doctrine_build.py` runs the build's `--check` against the committed pack. It passes
`--private-denylist` when `DOCTRINE_PRIVATE_DENYLIST` is set and `--private-skip` otherwise, because the general
test job and contributors' machines hold no secret; the CI step that always runs the private list is separate.
The same file proves the lint with throwaway inputs on a copy of the pack: a random token made up at run time is
handed to the word-list matcher and planted in a rule, and the build must fail; a made-up phone number in
international form and a room-id token, both assembled at run time, must fail the public list; a missing private
list must fail loud. No committed file holds a forbidden word, an encoding of one or a digest of one.

### The CI step

The *Validate* workflow (`.github/workflows/ci-validate.yml`, step "Doctrine pack current, true of the code and
lint-clean") runs `build_doctrine.py --check --core ... --jev ...` on every push and pull request. It byte-checks
the controller's copy of `compiled/` whenever that directory exists, runs the public list always, and runs the
private list from the repository's Actions secret `DOCTRINE_DENYLIST`: a JSON list of `[regex, why]` pairs.

- **Push, or a pull request from this repository** (release pull requests included): the secret is written to a
  file and checked. A missing or empty secret fails the build ("private denylist secret missing").
- **A pull request from a fork, or one Dependabot opened:** GitHub gives it no Actions secrets, so the step passes
  `--private-skip` and the skip is written to the job summary. The merge push runs the private list, so nothing
  such a pull request brought in reaches a release candidate unchecked.

**Create the secret before this step reaches `testing`.** Without it every push to `testing` fails *Validate*,
which blocks merges and **Promote**. `tests/test_doctrine_ci_step.py` runs the step's own shell with each of those
environments.

Only the doctrine outputs and the files listed under check 4 are linted. Running the private list over every
shipped path is a later change.

## Corrections to the sources (where the code wins)

These were stale or wrong in the advisor notes or in earlier drafts. The doctrine follows the code:

1. **Dryback units.** Dryback was described as points from peak. The controller computes
   `(peak - vwc) / peak * 100`, and `decide()` treats `dryback_target` as **relative**. DRY-02 makes the units
   explicit. Point bands and relative bands are kept apart.
2. **P1 exit.** Older notes say P1 ends when EC is at most `ec_target_p1 x 1.15`, or after 120 minutes. P1 has no
   time exit and no EC hold: it ends at max shots, or when a shot at the ceiling raises the peak by less than 0.5
   points (PH-5, PH-6).
3. **EC stacking switch.** The switch gates the **whole** P2 threshold EC steer in both directions
   (`p.stacking_on`). With it off, only dilute shots and `ec_adjust` act on EC (EC-15, CT-2). The offset it built
   keeps applying until the lights-on reset (the parameter map says so).
4. **Generative shot size.** The sources disagree (fewer bigger shots, or fewer smaller ones). CON-02 records the
   conflict and treats shot size as an EC and runoff lever.
5. **Stage arc.** One arc was hard-coded as a site's choice. It is now the `slab_default` **default** of an install
   setting (STG-06); `rockwool_default` stays a preview until its rows carry numbers.
6. **Second witness.** `decide()` fires the P1 ramp, the P2 top-up and the P3 emergency on the zone's single VWC
   reading. PRB-08 tells the brain to look for a second sign before acting on a trend. The watchdog is no
   probe-independent guard (`watchdog_due` needs VWC below the P2 threshold).
7. **Ramp cap.** `decide()` caps a ramp shot at `p1_initial + p1_incr x p1_max_shots`; the cap never binds.
8. **Settled pore EC.** The controller does the settling: `decide()` uses `ec_settled` when the caller supplies one
   and otherwise the raw `ec` (EC-07).
9. **Feed gate.** Each half of the source-water gate runs only when its feed sensor is configured and its band set;
   the feed sensors default to empty (the pH band ships set, the EC band does not). With no live feed EC reading
   the controller hands `decide()` an assumed feed EC of 3.0, and every dilutive test uses it. FEED-01 says so,
   and that a feed EC in the evidence may be that assumption (CT-6, CT-8, OD-2).
10. **P2 start in young plants.** RMP-10 and the coco start-up keep the vendor advice to hold P2 back until the
   daily dryback passes about 25 % relative, say plainly that the engine cannot, and name the nearest lever (a
   lower P2 threshold, never P2 off, never a lower rescue floor). Kept as advice: OD-1.
11. **Phase words.** BRN-07 points at the status tile's words (`zone_status_label()`), read from the code.
12. **What counts as a dead probe.** The controller sets a reading aside only when it is missing, unreadable, out
   of range or not updated for 20 minutes. That test reads Home Assistant's last-updated time, which an exactly
   repeated value does not move, so a truly frozen reading usually goes stale and is set aside. A value that keeps
   changing a little while stuck, or a sensor that forces an update, passes; PRB-02 tells the brain to name it.
13. **Smaller wording fixes.** CON-03: counters reset on the move into P0. EC-15's dilute shot names its two
   conditions and says the EC target is a person's setting.
14. **What `dryback_target` controls.** `decide()` compares it in two places only: P0's exit, against the drop since
   lights-on, and the predictive P3 test in the last 3 hours, which gives up when the needed drop would take more
   than 12 h and can never pass with a dark period of 12 h or more. It never sets the overnight dryback (PH-8 to
   PH-10, CT-4). DRY-02 says which drops it compares; the overnight levers are the dusk call and the re-water
   threshold notch (DRY-11); SYM-02, SYM-03 and SYM-04 forbid it as a lever; PH-11 shows that the integration's
   defaults (40 % generative, 50 % vegetative, a 120-minute wait) leave P0 to its timeout.
15. **The brain's action model.** The only numbers the brain writes are the zone's `p2_shot_size` and
   `p2_vwc_threshold` (`judge_levers()`, BR-5). Its other acting answers are dawn's start of the ramp, the ramp's
   hand-over, dusk's early stop, the salt judge's EC mode and the probe judge's set-aside (BR-1 to BR-4). The
   decision catalogue lists every question, its acting answers, their effect and code's guard; every `ACTS`
   lever names a decision and an answer that acts. Dusk's `continue_p2` acts on nothing (it cannot delay the
   engine's own P3), so SYM-04 lists the later end of the day as advice.
16. **Minimum daily floor.** Each zone's Min Daily Water Per Plant setting (the old hand-made helper on an older
   integration) times the plant count, defaulting to 0; the controller zeroes the floor for a zone whose table is
   backing up (CT-9, CT-10). Beyond the morning ramp, a fresh install has no guard that waters a zone whose probe keeps reading high
   (PRB-08, ACT-06, SYM-13).
17. **The Auto Setpoints learner.** With the room's switch on, `_follow_fc` moves field capacity toward the zone's
   highest counted reading of this grow-day or the one before and the P1 target toward the one before's, and on
   any field-capacity move of `FC_SHIFT_MIN` (1) point or more shifts the re-water threshold by the same amount,
   down too; each moves at most `FC_STEP_MAX` (1) point a grow-day, and neither it nor `wanted()` ever writes the
   rescue floor (CT-12, CT-13). The Setpoints question is asked only under that switch, and the band's centre is the last value
   the brain did not write, the learner's included (BR-5, H-11, ACT-07). Under the switch `over_saturated` marks
   each new high (CT-14), so the Over-water row and SYM-07 do not count it, and PRB-14 tells the brain to raise a
   field capacity and floor walking with a drifting probe for a person.
18. **Notches persist.** A setpoint notch is written to the zone's own number and stays; only the rescue-shot
   revert, a person's edit or a learner move replaces it (BRN-04). Phase calls, EC modes and set-asides are
   directives that expire. The notch is off while a grow plan owns the room (BR-5).
19. **Shots the maximum-EC block stops.** At maximum EC with a non-dilutive feed or a backed-up table, `decide()`
   blocks or holds before every other rule, so on that tick the P3 emergency, the watchdog and the floor do not
   fire either (IR-2). The dusk and night rows say so.

## Owner decisions

Places where this pack knowingly departs from the plain reading of the plan or from what a grower might expect of
the code, kept on purpose.

| # | Decision | Reason |
|---|---|---|
| OD-1 | **Vendor advice the engine cannot follow stays, as advice.** RMP-10 and the coco start-up keep "maintenance shots only once the daily dryback passes about 25 %" and say the engine cannot do it. | Growers read that guidance and will ask why the engine waters young plants in P2. The rule names the one lever that exists (a lower P2 threshold). A P2 start gate would be an engine change with its own soak, and would regenerate the doctrine. |
| OD-2 | **The assumed feed EC of 3.0 is documented, not changed.** FEED-01 and CT-8 describe what the code does with no feed sensor. ACT-05 tells the salt call not to rely on that test. | The doctrine may not contradict `decide()`. A code change that treats a missing feed EC as unknown would fail CT-8 until FEED-01 is reworded. |
| OD-3 | **Default stage arc `slab_default`.** | The vendor handbook and the slab guide agree on it. It is the default of a setting, never a hard-coded site choice. |
| OD-4 | **Vendor numbers in the arcs and substrate tables.** | Facts and numbers only, paraphrased and cited, tagged `vendor` so the brain weighs them below research. |
| OD-5 | **Shapes in the public list, words in the private one.** | A word in a shipped list publishes what it forbids. The cost is that a fork pull request is not checked for the private words; the merge push and every release pull request check them. |
| OD-6 | **Licence.** The rules drawn from the wiki pages paraphrase pages published under CC BY-NC 4.0 by their author. `LICENSE` records that author's grant of them under MIT for this pack. | The repository is MIT. Vendor, course and study content is facts and citations only. |
| OD-7 | **`dryback_target` is documented as the code uses it, and its defaults are left alone.** | Changing the defaults, giving the overnight dryback its own setting, or making predictive P3 work on 12-hour nights are engine and integration decisions with a soak. If one lands, PH-8 to PH-11 or CT-4 fail until the rules are reworded. |
